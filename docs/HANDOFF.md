## 성능이 실제로 올라갔다 — 근거 (실측, 추측 아님)

6번 단계에서 참조 구현(모두콘 챗봇) 스펙을 확인하고 임베딩 모델을 교체한 것이
**가장 큰 변화**였다. 아래는 같은 25문항 평가셋으로 실측한 수치다.

| 지표 | 이전(e5-small, 384차원) | 이후(EmbeddingGemma, 768차원) |
|---|---|---|
| 검색 hitRate(정답 근거가 상위에 있는가) | 0.91 | **1.00** |
| 관련/무관 질문 코사인 점수 겹침 | 있음(0.824~0.836 겹침 — 임계값으로 못 가름) | **없음(0.49~0.67 여유)** |
| 잘못된 차단(답할 수 있는 질문을 거절) | 3건/25 | **0건/25** |
| 검색 완전 실패(엉뚱한 근거로 확신에 찬 오답) | 2건/25 | **0건/25** |

그 위에 프롬프트 실험(인용 지시문 강화, 변수 하나만 변경)을 한 번 더 돌려서:

| 지표 | 실험 전 | 실험 후(채택) |
|---|---|---|
| 인용([id] 표시) 비율 | 32% | 45% |
| grounded 비율 | 95% | 100% |
| 평균 판정 점수(0-100) | 78.0 | 82.5 |

**결론: 오늘 작업으로 성능이 실측 기준 명확히 올라갔다.** 특히 "임베딩 모델
교체"가 이전 실패 사례를 전부 해결한 결정적 조치였다 — 도메인 튜닝이 아니라
모델 선택 자체의 문제였다는 뜻. 상세 표·원인 분석은 `docs/EXPERIMENTS.md`
전체(사이클 1~3) 참고.

## 6번 단계에서 무엇이 왜 바뀌었나

사용자가 모두의연구소 노드 커리큘럼 원문(로그인 필요해 직접 못 열람 —
사용자가 전문 붙여넣어 줌)을 확인시켜 준 뒤, 우리 초기 구현과의 차이를
점검하고 다음을 고쳤다.

- **임베딩**: `Xenova/multilingual-e5-small`(384d) → `onnx-community/embeddinggemma-300m-ONNX`(768d, dtype q4). 공식 프롬프트 템플릿(`task: search result | query: ` / `title: ... | text: `) 적용.
- **하이브리드 검색**: 가중합 방식 → 코사인 상위10 + BM25 상위5(중복 제거) 방식. 각 결과에 `method`(vector/bm25)와 방법별 점수 보존.
- **약한 근거 처리**: 하드 차단(LLM 호출 자체를 건너뜀) → 프롬프트 보수화 + UI 경고(결과는 버리지 않음). 임계값 0.55(원점수 코사인).
- **판정 스키마**: 2필드(근거성/거절적절성) → 6필드(`grounded·noHalluc·cited·refusal·score·comment`), 로컬 자기평가(`stream:false, think:false, format:"json", temperature:0`).
- **프롬프트 구조**: KST 현재 시각 컨텍스트, `[id]` 인용 규칙, 약한 근거 분기문 추가.
- **Ollama 상태 확인**: `GET /api/tags` 배너+재시도 — "엔진 꺼짐"과 "생성 실패" 구분.
- **PRD**: 비목표(3-1절), 검증 가능한 수용 기준(3-2절) 추가.
- **README.md 신규 작성**: 사용 조건(Ollama·다운로드 용량·CORS), OLLAMA_ORIGINS 설정법(mac/Windows/systemd), 설계 결정 요약.

기술 스택(Vite+React+TypeScript)은 커리큘럼 예시와 다르게 **순수 HTML/JS를
그대로 유지**하기로 결정했다 — 실제 채점 기준(Notion Main Quest 3 평가 문항
5개)이 프레임워크를 요구하지 않고, 위에 나열한 항목들이 전부 프레임워크와
무관한 동작·구조 문제였기 때문이다(사용자 확인 후 진행).
